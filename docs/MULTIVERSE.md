## 1. DIVERGENCE — measured

### ⚠ THE HEADLINE: THERE IS NO SHARED ENGINE. THERE IS NO SHARED CODE AT ALL.

The brief assumed a fork with common ancestry to measure. That is not what these two repos are.

| measurement | result |

| shared git commits | **0** — `git cat-file -t c44e72d` in `D:\lsw` → NONE |
| WAR WORLD root commit | `c44e72d` **2026-07-10** — "War World v1.0.0 — modern Three.js reimagining of Infantry Online" |

That single fact rewrites the plan. Read §2 before doing anything else.

## 2. WHAT ONLY WAR WORLD HAS

  a tuning layer: tyre compounds (slicks / all-terrain / knobblies / studded), gearing (stock /

- **An authoritative multiplayer server** — `ws`, a per-client input queue, server-side world.
- **Base building** (`sim/base.ts`, `sim/build.ts`), **buildings + interiors + indoor AI**
  (`building-generator.ts`, `interior.ts`, `indoor-ai.ts`, `building-navigation.ts`).
- **Military simulation**: `fireteam.ts`, `morale.ts`, `officer.ts`, `fronts.ts`, `influence.ts`,
  `military-missions.ts`, `k9-orders.ts`, `licenses.ts`, `arsenal.ts`.
- **TypeScript + vitest.** A test suite and a typechecker that Ascendants does not have.

## 4. THE LSWs IN WAR WORLD — and exactly what breaks

### Where they are defined

| file | what |
|---|---|
| `src/sim/types.ts:86` | `AscendantId` — a **40-member string union**. The type system's roster. |
| `src/sim/types.ts:766` | `Soldier.ascendant?: AscendantId` — **an LSW IS a Soldier**, not a separate entity |
| `src/sim/lsw.ts` (828 lines) | `LswDef` interface + `LSWS: Record<AscendantId, LswDef>` — 40 entries |
| `src/sim/lsw/*.ts` | **42 brain files**, one per unit: `step()` (bot cadence + passives) and `active()` (the pilot's Q) |
| `src/sim/lsw/index.ts` | the registry that imports all 42 |
| `src/sim/lsw/kit.ts` | shared target-sense so signatures fire strategically |

**Reach: 688 references across 84 files.**

### What an LSW actually is, in data

```ts
interface LswDef {
  id, name, faction, threat,          // identity
  lines: {inbound, landed, down, rampage},  // announcer VO — keyed to audio files
  scale, speed, color,                // embodiment
  activeLabel, activeCd, energyRegen?,// the one signature ability
  weapon: WeaponId,                   // → arsenal.ts, the `lsw_*` family
  moves?, rig?, prop?, attackPose?, flies?   // model + movement class
}
```

⚠ **There is no HP, no attribute block and no progression here.** A War World LSW is *a Soldier with
a scale/speed/colour override, one signature weapon and one active*. Ascendants' fighter carries
seven attributes, seven ability slots, a rank, resistances, talents, gear, evade tech, a flight tier,
a frame, an origin, a psyche and a career.

**That asymmetry is the whole Passport problem, and it is good news:** War World needs a *narrow*
projection of a rich character, not a merge of two equals.

### What breaks if they are removed

| system | how it breaks |
|---|---|
| `arsenal.ts` | the entire `lsw_*` weapon family loses its owners |
| announcer VO | 4 lines × 40 units, with generated audio keyed by id (`ann_<id>_<moment>`) |
| drops / economy | `LswDrop`, and the `'dna'` pickup whose payload **is an ascendant id** |
| events / feed | `'lsw_active'` carries an ascendant id as its text |
| the director | deploys LSWs by threat tier; `threat: 4` is defined and **used by nobody** |
| campaign / career | LSW ownership, hiring, the two factional stables |
| **the type system** | `AscendantId` is a closed union — deleting members is a **compile error at every one of the 84 call sites**, which is exactly what you want: the typechecker will walk you through the whole replacement |

⚠ **Do not delete the seam — replace what fills it.** `Soldier.ascendant?: AscendantId` is already
the projection point. The job is to make `AscendantId` and `LSWS` come from the shared roster instead
of from a hand-written union.

## 5. THE ARCHITECTURE — what I would build

### ⚠ The measurement changes the design

You cannot have "one engine, many games" — there is no shared engine, and forcing one would mean
throwing away either War World's server, models, vehicles and tests, or Ascendants' entire
simulation design. **Both would be a catastrophe.**

What you can have is better, and it is what actually makes the multiverse idea travel:

> **ONE CONTRACT, MANY ENGINES.**
> A product is free to be TypeScript or JavaScript, isometric or first-person, client-only or
> server-authoritative — as long as it can *read a Passport* and *write a Ledger entry*.

That is also the only version of this that lets a third product (your space game, an FPS, someone
else's isometric build) join without asking permission from either existing codebase.

### The four layers

```
   THE PASSPORT   one character. identity + attributes + progression + origin.
                  engine-neutral JSON. NO per-game stats.
        ↓
   THE PROJECTION per dimension. Turns Passport attributes into THAT engine's numbers.
                  Lives WITH the engine, never with the passport.
        ↓
   THE GATE       the dimensional door. What travels, what is confiscated, what is learned.
        ↓
   THE LEDGER     shared progression, ownership, career. The live-service spine.
```

**Strength is Strength. What changes is what Strength BUYS in a world.** A rank-79 Ascendant in
The Ascend lifts an airliner; the same rank in War World is a unit a fireteam must plan around, and
in PowerWorld it is a mid-card flier. One number, three readings.

### On your specific questions

**"Is it a different UI, or a different AI, when you cross?"**

- **UI: different SHELL, same substrate.** A shell is *camera + controls + HUD*. That is the
  extraction already queued for Ascendants. The substrate must never know which shell is attached —
  that is what makes an FPS for you and an isometric game for Chris the *same game underneath*.
- **AI: same brain, different actuator.** Ascendants' AI already emits an **intent**
  (`{move, aimDir, slots, fly}`) that both the player and the bot route through — that is a
  shell-neutral seam and it is the right one. War World's LSW brains act on the world directly
  (`step(w, s)`), so they are *not* portable as written. Porting the intent shape into War World is
  the smaller job of the two and should happen before any character crosses.
- **Balance: this is the Projection's entire job**, and your instinct is exactly right — a thing
  arriving from another dimension has to be re-expressed in local terms, or it is either a god or a
  joke.

**"Would my friend need a client to download?"**

- **For Ascendants: no.** It is browser Three.js. A URL is the whole client, and Vercel can host it.
- **For War World: no client, but yes a server.** `src/server/server.ts` is a **persistent Node
  WebSocket process**. Vercel's static/serverless hosting **cannot** run it. You need a
  process host (Railway, Fly.io, Render, a VPS) for the server, and Vercel can still serve the
  client that talks to it.
- **Dev multiplayer today** is therefore easiest in War World (the server exists) and needs building
  in Ascendants (`net.js`/`netplay.js` are scaffolding, not a server).

**"Could it seamlessly be an MMO / live service?"**

Honestly: **live service yes, MMO not without a different plan.** War World's server is authoritative
with an input queue, which is the correct foundation for competitive multiplayer and for a persistent
Ledger. "MMO" adds sharding, persistence at scale, and anti-cheat economics that are a different
project. The Ledger (§5) is the piece that makes it a *live service* — shared progression across
products is the feature nobody else has, and it does not require an MMO to ship.

**On the models:** War World's `LswDef` already separates *identity* (id, name, faction) from
*embodiment* (rig, prop, attackPose, scale, colour). **The models can almost certainly be kept and
re-skinned** — a shared character maps onto a rig/prop/pose triple. What cannot be kept for free is
the **VO**: 4 lines × 40 units of generated announcer audio keyed by id. Replacing the roster means
regenerating it — scriptable (`tools/gen-lsw-vo.mjs` already exists), but budget for it.

## 6. QUESTIONS I NEED ANSWERED

1. **Naming.** Is the *product* called PowerWorld and the *dimension* something else? Right now one
   word means two things and every document after this inherits the confusion.
2. **Which repo owns the Passport schema?** My recommendation: **neither** — a third, tiny repo (or a
   `packages/passport` folder) that both read, so the contract cannot be owned by one game's release
   cycle.
3. **Are War World's 40 LSWs to be deleted, or re-mapped?** Deleting loses 42 hand-written brains and
   their VO. Re-mapping keeps the embodiment and swaps the identity. Canon says the roster is one —
   it does not say the brains must be thrown away.
4. **Does War World keep its own progression, or read the Ledger?** This decides whether a character
   levelling in War World levels in The Ascend.
5. **TypeScript or JavaScript for the shared contract?** JSON schema is neutral, but the *readers*
   are not. War World will want types.
6. **What is the first thing you want to SEE working?** My recommendation is the smallest possible
   proof: one Ascendants fighter standing in War World with correctly projected numbers. Everything
   else is downstream of that working once.
